# The provenance records regenerate machine-independently
Status: implemented

## Problem

Two tracked provenance records rewrote themselves (byte-different) whenever
a fresh environment ran the ensure/build path, dirtying every worktree and
stamping every receipt "(dirty working tree at receipt time)":

- `presentation/official-web/MANIFEST.sha256` (the vendored dist's digest
  record): the committed bytes were spelled in shasum's BINARY marker form
  (`digest *./path`) — the Windows default of the machine that first
  generated it — while `build-upstream.sh` (D15: the build re-records this
  record) regenerates in the macOS/Linux text form (`digest  ./path`).
  Same 89 digests, all 89 lines differ: a full-file rewrite per environment.
- `presentation/official-web/client-bundles/ROSTER.json` (the derived
  W-SHELL roster, regenerated by `build-client-bundles.sh` via
  `roster.mjs`): its `dir`/`bundle` fields embedded the generating
  machine's ABSOLUTE work path — the committed value names a Windows Temp
  dir (`C:\Users\13957\...\dsh-harness-src\packages\...`); any
  regeneration wrote `/tmp/dsh-harness-src/...` instead.

## Decision

- `build-upstream.sh` now pins `-t` (text record spelling), matching what
  its sibling build already did for `MANIFEST.sha256.computed`; the
  committed dist manifest is re-recorded once in that spelling (digests
  and paths byte-unchanged, only the marker character normalized).
- `roster.mjs` records `dir`/`bundle` as checkout-relative POSIX paths;
  the one consumer (the copy leg in `build-client-bundles.sh`) joins them
  against the work checkout root, which it already holds in `$WORK`.

## Alternatives considered

- gitignoring the two records: rejected — they ARE the provenance claim
  (D15: the committed record is the reference the ensure scripts verify
  against); untracking them would trade a cosmetic dirty for a real hole.
- Pinning the work dir spelling (`/tmp/dsh-harness-src`) into the records
  instead of relativizing: rejected — it only moves the machine dependence
  (a Windows host regenerates a different spelling); relative-to-checkout
  is machine-free by construction.
- Verifier-side normalization (teach `shasum -c` consumers to ignore the
  marker): rejected — the consumers already accept both spellings; the
  instability is on the producing side, which is also the smaller fix.

## Consequences

A fresh clone → ensure → regenerate cycle now leaves both records
byte-stable, and receipts stop carrying an inherited dirty marker. The
next full regeneration (network or local-submodule build) is the proof:
`git diff` on the two records must stay empty.
